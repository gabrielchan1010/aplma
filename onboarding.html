The Problem

Most covenant breaches
are preventable.

SME corporates sign facility agreements with hundreds of obligations buried across the document — definitions, restrictions, permitted carve-outs. Those obligations interact with every other contract the company signs.

When two contracts conflict, the borrower often doesn't notice until a lender raises it. By then the legal fees to fix it dwarf what it would have cost to catch in advance.

Step one in preventing this: making every obligation visible.

What This Prototype Does

Hand it a PDF.
Get one covenant, end-to-end.

This prototype tests whether the workflow holds up: parse the agreement, locate the right pages, lift the verbatim text, and present it page-linked for verification. Right now it handles one negative covenant — the restriction on Financial Indebtedness — along with the Financial Indebtedness and Permitted Financial Indebtedness defined terms it relies on.

If the output is reliable enough for a lawyer to trust, the same pipeline extends to other covenants (Disposals, Negative Pledge, Information Undertakings, and so on). Your review is what decides whether — and how — we expand.

You give it

A facility agreement as a PDF. Up to a few hundred pages.

You get back

An HTML report with the restriction clause and the defined terms it depends on (Financial Indebtedness and Permitted Financial Indebtedness) — each page-linked so you can verify before you trust.

How It Works

Five steps, 3–5 minutes per document.

A mix of local AI (Docling, on the Colab runtime) for parsing, cloud AI (Google Gemini) for navigation, and plain Python for lifting verbatim text.

1
Docling Ingest

Docling reads the PDF and detects its structure.

2
Gemini Read TOC

Google's Gemini vision model reads the contents pages as images.

3
Gemini Scout

Find the pages holding each covenant.

4
Python Slice

Pull the text from those exact pages.

5
Python Extract

Lift verbatim text into the report.

Why this matters for you: AI is only used to find which pages to read — the actual clause text is lifted character-for-character from the PDF, not paraphrased. The Gemini steps send page images / text to Google; the Docling and Python steps run on the Colab machine. See the next slide for what this means for your document.

Under the Hood · Tunability

The extraction rules
live in plain text.

Every extraction is driven by a short YAML "spec" — a human-readable file listing the phrases the tool searches for. The Scout (Step 3) uses the search terms; the structural parser (Step 5) uses the literal definition openings and restriction heading.

If an agreement uses non-standard wording, the spec is editable without touching code. Today there's one spec — for the restriction on Financial Indebtedness.

What this means for you: the rules driving the extraction are visible, not hidden inside the model. A copy of the active spec is included at the bottom of every report you generate, so you can audit exactly what was searched for.

aplma/specs/financial_indebtedness.yaml
# Tells the tool how to find the
# "Financial Indebtedness" clauses.
# Edit the lists below if a new
# agreement uses different wording.

search_terms:
  - "Financial Indebtedness"
  - "Permitted Financial Indebtedness"

definition_openings:
  financial_indebtedness:
    - "Financial Indebtedness means"
  permitted_financial_indebtedness:
    - "Permitted Financial Indebtedness means"

restriction_heading:
  - "Financial Indebtedness"

Tech Stack

What's powering this.

Three pieces, behind the scenes. You don't interact with these directly.

Docling

Open-source library that reads the PDF and detects its structure (headings, clauses, tables).

Google Gemini

Google's AI model. We use it for two narrow jobs: reading the TOC, and identifying which pages contain each covenant. Requires an API key (free tier is plenty).

Python (in Google Colab)

A free, browser-based notebook environment from Google. You don't install anything — the code runs on Google's servers.

Before You Upload — Please Read

Your document will leave your computer.

This is a prototype tool. It runs in Google's infrastructure and uses Google's Gemini API. That means parts of your facility agreement are sent to Google during processing.

Use sample, anonymised, or non-confidential documents while evaluating the tool. For real client matters, check first with your firm's data-handling and confidentiality policies — particularly any rules about sending client documents to third-party cloud services.

Google's terms for the free Gemini API and Colab apply. No data ever flows to Enblock from this tool.

What goes where
1
PDF upload → Colab runtime

Your file is uploaded to a temporary Google Colab virtual machine. It's wiped when the session ends.

2
TOC pages → Gemini API

Images of the contents pages are sent to Google's Gemini servers for text extraction.

3
TOC text + search results → Gemini API

A short text prompt with the contents listing and heading matches is sent to Gemini to identify page ranges. The full document text is not sent.

4
Extraction → stays local

All clause extraction and the final HTML report happens on the Colab runtime — no further calls to Google.

If Something Goes Wrong

Three common hiccups.

If you see one of these, here's the fix.

!
"GEMINI_API_KEY not set"

Your secret's Notebook access toggle is off. Go back to the key icon on the left, find your secret, and switch it on.

!
"Runtime disconnected"

Colab idles out after ~90 minutes. Just click Reconnect in the top-right and run all cells again.

!
"The extraction looks wrong"

The report always shows source-page snapshots — check those. If the tool fetched the wrong pages, send me the PDF and I'll tune the spec for that agreement style.
